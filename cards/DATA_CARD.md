# Data Card: Py5cheSim DQN Training Data

## Card Status

**Status:** Working document  
**Project:** Formally Verified DQN-Based O-RAN Scheduler

This card will be updated as the training dataset, traffic scenarios, and
hardware-validation stages evolve.

Status labels used throughout this document:

- **[Known]** - already implemented, observed, or recorded.
- **[Proposed]** - planned but not yet fully evaluated.
- **[TBD]** - information that still needs to be measured or documented.

---

## 1. Dataset Summary

**[Known]**

The learning data is generated synthetically through the Py5cheSim
simulation environment.

It is not a conventional pre-collected static dataset.

The DQN learns from simulated interactions represented as transitions:

```text
(
    current_state,
    action,
    reward,
    next_state,
    terminal
)
```

These transitions are stored temporarily in experience replay during
training.

---

## 2. Dataset Purpose

**[Known]**

The purpose of the data is to train a DQN to select resource-allocation
weights for three network slices:

```text
eMBB
URLLC
mMTC
```

The model learns a mapping:

```text
network state
    ->
slice-resource weight action
```

The resulting policy is intended for later integration with an O-RAN
near-RT RIC and OpenAirInterface scheduler.

---

## 3. Data Source

**[Known]**

Training observations are generated by Py5cheSim rather than collected
from human participants or a production cellular network.

The primary simulation sources include:

```text
formal-verification/py5chesim/formal_vanilla_v2.py
formal-verification/py5chesim/simulation_formal.py
formal-verification/py5chesim/Cell.py
formal-verification/py5chesim/Slice.py
formal-verification/py5chesim/UE.py
```

Network behavior is produced by simulated:

- user equipment,
- packet flows,
- network slices,
- schedulers,
- traffic conditions,
- resource utilization,
- packet transmission,
- and packet-loss behavior.

---

## 4. Main Data Characteristics

**[Known]**

Each DQN observation contains three values:

```text
[
    eMBB state,
    URLLC state,
    mMTC state
]
```

The order is fixed:

```text
0 -> eMBB
1 -> URLLC
2 -> mMTC
```

The training implementation derives the state from Py5cheSim scheduler
information and caps each component at:

```text
500
```

The neural-network input is normalized as:

```text
normalized_state = raw_state / 500.0
```

Therefore each model input is expected to fall approximately within:

```text
[0.0, 1.0]
```

---

## 5. Actions Associated With the Data

**[Known]**

Each transition contains one of 22 predefined actions.

Each action represents:

```text
[eMBB weight, URLLC weight, mMTC weight]
```

Examples include:

```text
[0, 100, 0]
[20, 80, 0]
[40, 40, 20]
[20, 40, 40]
```

The action is selected either through the DQN policy or the exploration
mechanism used during training.

---

## 6. Reward Information

**[Known]**

Rewards are generated automatically by the simulation.

No human annotators assign labels or scores.

The reward considers simulator-derived quantities including:

- slice service satisfaction,
- radio-resource utilization,
- overall resource efficiency,
- URLLC packet delivery,
- and a URLLC safety penalty.

The training implementation contains the safety condition:

```text
URLLC state >= 1
and
URLLC action weight < 20
```

When this condition is true, the reward receives a safety penalty.

The code applies:

```text
-2.0 * safety_penalty
```

and also includes a URLLC delivery term.

---

## 7. Collection Method

**[Known]**

Data is generated online during reinforcement-learning episodes.

The basic collection process is:

```text
simulate current network state
        |
        v
construct three-slice observation
        |
        v
select DQN/exploration action
        |
        v
apply simulated allocation
        |
        v
observe network outcome
        |
        v
calculate reward
        |
        v
construct next state
        |
        v
store transition in replay memory
```

The formal-v2 implementation is configured for:

```text
20,000 training episodes
```

with replay-memory capacity:

```text
10,000 transitions
```

Training begins after at least:

```text
500 transitions
```

are available.

## 9. Annotation

**[Known]**

There is no manual annotation.

Labels such as action, reward, service satisfaction, utilization, and packet
delivery outcomes are produced automatically by the simulator and learning
process.

Therefore annotation error from human labelers is not a concern.

However, simulator assumptions and implementation errors can still introduce
systematic error.

## 10. Intended Uses

**[Known]**

The data is intended for:

- training the project's DQN scheduler,
- evaluating learning behavior in Py5cheSim,
- producing candidate scheduling policies,
- studying three-slice resource allocation,
- and supporting formal verification of a selected frozen model.

**[Proposed]**

Future uses may include:

- comparison with non-learning schedulers,
- testing additional traffic mixtures,
- robustness testing,
- additional congestion scenarios,
- and comparing simulated behavior with OAI/USRP measurements.

---

## 11. Uses Outside the Current Scope

The current training data should not automatically be treated as
representative of:

- all 5G networks,
- all O-RAN deployments,
- all UE populations,
- all channel conditions,
- all mobility conditions,
- all traffic distributions,
- uplink scheduling,
- commercial operator traffic,
- or real-world RF environments.

The training data was created for a specific research prototype.

---

## 12. Potential Biases

**[Known / Anticipated]**

The strongest source of potential bias is simulation design.

The learned policy may reflect:

- the traffic patterns chosen for Py5cheSim,
- the number of simulated UEs,
- slice configurations,
- simulator channel assumptions,
- scheduler implementation,
- reward design,
- resource-allocation rules,
- and the range of states encountered during training.

The explicit URLLC reward and safety terms intentionally bias the learning
process toward protecting URLLC traffic.

This is a design choice rather than a neutral representation of all possible
network objectives.

---

## 13. Coverage Limitations

**[Known]**

The state representation contains only three values.

Consequently, the DQN does not directly observe variables such as:

- detailed per-UE channel quality,
- CQI distributions,
- mobility,
- individual latency,
- per-UE buffer state,
- interference,
- HARQ state,
- or physical-layer conditions.

These effects may influence network performance without being explicitly
represented in the learning state.

---

## 14. Simulation-to-Reality Limitation

**[Known]**

The training data is synthetic.

The deployed model later receives state information from an OAI/FlexRIC
system rather than directly from Py5cheSim.

Although both systems use a three-element normalized state, identical
numerical representation does not guarantee identical real-world semantics.

This creates a potential:

```text
simulation-to-reality gap
```

that must be evaluated experimentally.

**[Proposed]**

USRP and real-UE validation will be used to investigate this limitation.

---

## 15. Privacy

**[Known]**

The current training dataset contains synthetic network simulation data.

It does not intentionally contain:

- names,
- personal identifiers,
- subscriber identities,
- user-generated content,
- or human-subject data.

Therefore the present training data has low direct privacy risk.

Future datasets collected from real cellular systems should be reviewed
separately before publication.

---

## 16. Ethical Considerations

The model controls allocation of shared communication resources.

Poorly designed training data or reward functions could cause:

- unfair resource distribution,
- starvation of some traffic classes,
- degraded quality of service,
- or unexpected behavior under unseen conditions.

The project therefore combines learning with:

- constrained action choices,
- formal verification,
- runtime safety checks,
- and work-conserving scheduler enforcement.

---

## 19. Data Card Summary

The current learning data is:

```text
synthetic
simulation-generated
three-slice
reinforcement-learning data
```

Its principal strength is controlled generation for training and testing the
DQN scheduling concept.

Its principal limitation is that simulation-generated behavior may not fully
represent real O-RAN and RF conditions.

This data card should therefore be updated whenever the traffic scenarios,
state definition, training dataset, or hardware evaluation process changes.
