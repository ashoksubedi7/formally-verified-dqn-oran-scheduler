# Data Card

1. Dataset

The learning data is generated synthetically through the Py5cheSim simulation
environment.

It is not a conventional pre-collected static dataset.

The DQN learns from simulated interactions represented as transitions:

```text
(
    current_state,
    action,
    reward,
    next_state,
    terminal
)
```

These transitions are stored temporarily in experience replay during training.

2. Dataset Purpose

The purpose of the data is to train a DQN to select resource-allocation weights
for three network slices:

```text
eMBB
URLLC
mMTC
```

The model learns to map:

```text
network state
    ->
slice-resource weight action
```

The resulting policy is intended for integration with an O-RAN near-RT RIC
and OpenAirInterface scheduler.

3. Data Source

Training observations are generated by Py5cheSim rather than collected from
human participants or a production cellular network.

The primary simulation sources include:

```text
formal-verification/py5chesim/formal_vanilla_v2.py
formal-verification/py5chesim/simulation_formal.py
formal-verification/py5chesim/Cell.py
formal-verification/py5chesim/Slice.py
formal-verification/py5chesim/UE.py
```

Network behavior is produced by simulated:

- packet flows;
- network slices;
- schedulers;
- resource utilization;
- packet transmission;
- packet-loss behavior.

4. Main Data Characteristics

Each DQN observation contains three values:

```text
[
    eMBB state,
    URLLC state,
    mMTC state
]
```

The training implementation derives the state from Py5cheSim scheduler
information and caps each component at:

```text
500
```

The neural-network input is normalized as:

```text
normalized_state = raw_state / 500.0
```

Therefore, each model input is expected to fall approximately within:

```text
[0.0, 1.0]
```

5. Reward Information

Rewards are generated automatically by the simulation.

No human annotators assign labels or scores.

The reward considers simulator-derived quantities including:

- slice service satisfaction;
- radio-resource utilization;
- overall resource efficiency;
- URLLC packet delivery;
- a URLLC safety penalty.

The training implementation contains the safety condition:

```text
URLLC state >= 1
and
URLLC action weight < 20
```

When this condition is true, the reward receives a safety penalty.

The code applies:

```text
-2.0 * safety_penalty
```

6. Collection Method

Data is generated online during reinforcement-learning episodes.

Data is collected from simulated network-state observations and stored in
replay memory.

7. Dataset Size

The replay buffer can contain at most:

```text
10,000 transitions
```

at one time.

The complete number of transitions generated during the selected training run
has not yet been recorded as a fixed dataset statistic.

The project currently preserves the trained model and training source rather
than a complete exported transition dataset.

8. Annotation

There is no manual annotation.

Labels such as:

- action;
- reward;
- service satisfaction;
- utilization;
- packet delivery outcomes;

are produced automatically by the simulator and learning process.

Therefore, annotation error from human labelers is not a concern.

However, simulator assumptions and implementation errors can still introduce
systematic error.

9. Intended Uses

The data is intended for:

- training the project's DQN scheduler;
- evaluating learning behavior in Py5cheSim;
- producing candidate scheduling policies;
- studying three-slice resource allocation;
- formal verification of a selected frozen model.

10. Uses Outside the Current Scope

The training data was created for a specific research prototype and should not
automatically be treated as representative of:

- all 5G networks;
- O-RAN deployments;
- channel conditions;
- commercial operator traffic;
- real-world RF environments.

11. Potential Biases

The strongest source of potential bias is simulation design.

The learned policy may reflect:

- the traffic patterns chosen for Py5cheSim;
- the number of simulated UEs;
- simulator channel assumptions;
- reward design.

The explicit URLLC reward and safety terms intentionally bias the learning
process toward protecting URLLC traffic.

This is a design choice rather than a neutral representation of all possible
network objectives.

12. Coverage Limitations

The state representation contains only three values.

Consequently, the DQN does not directly observe variables such as:

- detailed per-UE channel quality;
- individual latency;
- HARQ state;
- physical-layer conditions.

These effects may influence network performance without being explicitly
represented in the learning state.

13. Simulation-to-Reality Limitation

The training data is synthetic.

The deployed model later receives state information from an OAI/FlexRIC system
rather than directly from Py5cheSim.

Although both systems use a three-element normalized state, identical numerical
representation does not guarantee identical real-world semantics.

This creates a potential simulation-to-reality gap that must be evaluated
experimentally.

USRP and real-UE validation can be used to investigate this limitation.

14. Privacy

The current training dataset contains synthetic network simulation data.

It does not intentionally contain:

- names;
- subscriber identities;
- user-generated content.

Therefore, the present training data has low direct privacy risk.

15. Ethical Considerations

The model controls allocation of shared communication resources.

Poorly designed training data or reward functions could cause:

- unfair resource distribution;
- starvation of some traffic classes;
- degraded quality of service;
- unexpected behavior under unseen conditions.

16. Evaluation Data

The selected model has already been evaluated outside Py5cheSim through:

- formal verification of a URLLC safety property;
- RFsim integration;
- three-slice congestion testing;
- RB-level scheduler validation.

These runtime experiments are not part of the original Py5cheSim training
dataset.

They provide separate post-training evidence.

17. Future Data Improvements

Future versions of this card should document:

- exact traffic distributions;
- UE counts per scenario;
- congestion levels;
- channel-condition variation;
- real-RF test data.
